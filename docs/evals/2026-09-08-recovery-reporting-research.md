# Recovery reporting research — 2026-09-08

The authorized contract is to report observed resumed work reliably. It does not prove that the user's whole task finished successfully.

## Evidence and implementation consequences

- **Discord acknowledgement:** Execute Webhook with `wait=true` waits for server confirmation and returns the created message. With the default `wait=false`, a message that was not saved need not produce an error. Require the returned message ID before recording delivery. [Discord webhook reference](https://docs.discord.com/developers/resources/webhook)
- **Retries:** Respect Discord's response delays and rate-limit headers. Discord explicitly says to stop using a webhook after a 404, and avoid repeated invalid-token or forbidden requests. Keep undelivered events durable, expose the configuration problem, and resume after repair; do not hammer a deleted webhook. [Discord rate limits](https://docs.discord.com/developers/topics/rate-limits)
- **Persistence:** A separate success-state write and notification write create a crash gap. Persist the outbox event before clearing the pending observation; replay safely using a stable recovery ID. This applies the transactional-outbox principle to local files without requiring a database. Discord acceptance followed by a lost response/local crash can still produce duplicates; the cited webhook API does not promise an idempotency key for Execute Webhook. [AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
- **Codex:** `turn/completed` also represents interrupted or failed turns. Check its status. `thread/resume` can return old history and replay persisted token usage, so those alone are not fresh progress. Correlate thread/turn and observe new assistant/tool items or deltas after the recovery baseline. Generate schemas with the installed Codex version when validating concrete field names. [Codex app-server reference](https://github.com/openai/codex/blob/eaf81d3f/codex-rs/app-server/README.md)
- **Claude:** Partial streaming messages are optional. Complete assistant messages remain available without them. Tool-call content is produced before tool execution and before the final result. Support both text and tool work; do not equate initialization or a generic message boundary with successful progress. SDK envelopes do not establish the exact native transcript format. [Claude streaming output](https://platform.claude.com/docs/en/agent-sdk/streaming-output)
- **Pi:** RPC prompt responses acknowledge acceptance/queueing; agent events arrive asynchronously afterward. Acceptance is not proof of recovery. An upstream user report describes an older release announcing retry success before tool execution finished; treat that report as a regression scenario, not proof of current installed behavior. [Pi RPC reference](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/rpc.md), [version-specific issue](https://github.com/badlogic/pi-mono/issues/2905)
- **Delayed observation:** No reviewed primary source establishes ten minutes as an upper bound on agent recovery. Keeping a pending observation across restarts and long pauses is a design inference consistent with the requested contract. Bind it to session/request identity plus a persisted baseline, and terminate it on verified replacement or definitive failure. Otherwise later unrelated work could be misattributed. Trace context illustrates why operation identity matters. [OpenTelemetry traces](https://opentelemetry.io/docs/concepts/signals/traces/)
